1.3 Hard constraints (never violate)
• No LLM or generative-AI model or API anywhere in the runtime pipeline. Classification uses rules and scikit-learn-class models only; extraction stays deterministic too (privacy, reproducibility, zero cost). 4. SYSTEM & FUNCTIONAL REQUIREMENTS


=== SECTION ===
4.1 Scope
In scope: everything in the source PDF — multi-bank input, text and image PDFs, multiple layouts, account details, the five transaction fields, non-LLM classification, and xlsx/csv export including the category.
Out of scope for v1 (design the extension points only): credit-card statements (detect and warn), non-PDF inputs, bank or Account-Aggregator APIs, multi-currency conversion, billing, native mobile apps.
4.2 Processing contract and statuses
Each stage is a pure, independently testable unit with typed inputs and outputs (dataclasses or Pydantic). The orchestrator records per-stage timings, per-page status and warnings, and degrades gracefully: a failed page or stage yields partial results plus warnings, not a failed file. Statuses: QUEUED → INSPECTING → NEEDS_PASSWORD → EXTRACTING → PARSING → VALIDATING → CLASSIFYING → READY | READY_WITH_WARNINGS | FAILED. Processing is idempotent and resumable; reprocess never discards manual edits (they are re-applied by a stable row key).
4.3 Intake and validation
• Multi-file drag-and-drop and file picker; stream uploads to disk, never hold them in memory. Validate %PDF- magic bytes in the first 1 KB (not the extension or MIME type), non-zero size, size and page limits; compute SHA-256 for duplicate detection (offer “open existing”).
• Never execute PDF actions or JavaScript; flag files containing /JavaScript, /Launch or /EmbeddedFile.
• Encrypted PDFs: try the empty password, otherwise set NEEDS_PASSWORD and show a dialog (wrong password → inline error, retry or skip). Decrypt to a temporary copy with pikepdf; the password lives only in memory for the duration of the job.
• Damaged PDFs: one automatic repair attempt (pikepdf/qpdf); otherwise fail with the specific code PDF_CORRUPT.
• Store the original under a random UUID path (never served statically), optionally Fernet-encrypted at rest. Return 202 immediately and do all heavy work off the request thread.


=== SECTION ===
4.4 PDF type detection (per page, then per document)
Compute for each page: meaningful native character count, text-area coverage, garbage-character ratio (U+FFFD, private-use characters, (cid:N) sequences), full-page image coverage, presence of invisible text (render mode 3) and page rotation.
• TEXT: enough meaningful text (at least 40 characters on a page expected to hold transactions), garbage ratio below 5 %, not dominated by a full-page image.
• IMAGE: negligible native text with large image coverage, or garbage ratio of 5 % or more (broken font encodings count as image).
• HYBRID: a native text layer exists but is untrustworthy (for example an invisible, low-quality OCR layer) → run both paths and keep the one with the better table-parse and reconciliation score.
• Document type = TEXT, IMAGE or MIXED. Show it in the UI with the reason, allow a Force OCR re-run, and persist the decision features for debugging.


=== SECTION ===
4.5 Native text extraction
Use pdfplumber / pdfminer.six for words with coordinates and for lines/rects (ruled-table evidence), and pypdfium2 for rendering (both permissively licensed; mention PyMuPDF only as an alternative if AGPL is acceptable). Emit the shared Word model {page, text, x0, y0, x1, y1, conf, source: native|ocr} with coordinates normalized to 0–1 plus the stored page size, so both extraction paths and the UI overlays use identical geometry.


=== SECTION ===
4.6 OCR pipeline (image and hybrid pages)
1. Render at 300 DPI (cap total pixels; drop to 200 DPI for oversized pages).
2. Preprocess with OpenCV: grayscale → orientation fix (Tesseract OSD, 0/90/180/270) → deskew (±15°) → denoise → CLAHE contrast → adaptive threshold (keep both gray and binary variants) → upscale if effective DPI is below 200. Keep a ruling-line map from morphology for column detection.
3. Tesseract (--oem 1): --psm 6 for the table body with --psm 4 and --psm 11 fallbacks; use word-level TSV output for boxes and confidences.
4. Numeric second pass: once column boundaries are known, re-OCR cropped Date/Debit/Credit/Balance cells with a digit whitelist (0-9 . , - ( ) C R D). Verify whitelist support on the installed Tesseract version; if it is ignored, fall back to post-hoc character mapping.
5. Mark words with confidence below 60; compute a per-page OCR quality score; if the table-parse and reconciliation score is poor, retry with alternate preprocessing/psm and keep the best result.
6. Process pages in parallel (process pool) with per-page timeouts and memory caps. Keep OcrEngine pluggable (PaddleOCR or docTR adapters possible later; not shipped by default).


=== SECTION ===
4.7 Layout and table reconstruction (shared by the native and OCR paths)
1. Lines. Cluster words by y-centre with an adaptive tolerance (about 0.5 × median word height); sort each line by x.
2. Header detection. Find lines where at least 3 tokens fuzzy-match (RapidFuzz ≥ 85, tolerant of OCR noise) the header synonym dictionary: Date / Txn Date / Value Date / Post Date; Narration / Particulars / Description / Transaction Remarks / Details; Chq / Ref No. / Instrument No.; Withdrawal / Debit / Dr; Deposit / Credit / Cr; Amount; Balance / Closing Balance. Merge two-line headers (for example “Withdrawal” above “Amt.”).
3. Columns. Derive boundaries from header extents, then refine them with body evidence: cluster the right edges of numeric tokens (amounts are right-aligned) and the left edges of dates; reconcile mis-centred headers; use ruling lines when present.
4. Rows. A new transaction starts where the date cell parses as a date. Lines without a date are continuation lines: append them to the description, and attach orphan amounts to the previous row if it lacks them. A row may legitimately have only one of Debit or Credit.
5. Pages. Reuse the previous page’s columns when the header is not repeated. Remove running headers, footers and watermarks by repetition (same text at the same y across pages) and by pattern (“Page x of y”, “system generated statement”, legal footers). Stop at terminators such as “Closing Balance”, “Statement Summary”, “End of Statement”, “Legends”.
6. Strategy cascade with scored selection. (a) bank-profile strategy → (b) generic header-anchored → (c) ruled-table extraction (lines/rects) → (d) whitespace/stream clustering. Run them in order but choose the winner by score = share of rows passing the running-balance check × date-parse rate × column-fill rate. Record the winning strategy on the statement.
7. Bank profiles (bank_profiles/*.yaml): header aliases, date formats, column order, Dr/Cr conventions, skip patterns, terminators and known quirks. Ship profiles for the D3 banks and a generic.yaml for everything else. Adding a bank must need no code change. Because no real statements are supplied, mark every profile verified: false and say so in the docs; the generic engine must carry the load.
8. Support landscape and rotated pages and, best effort, two tables side by side on one page.


=== SECTION ===
4.8 Parsing and normalization
• Dates. Support DD/MM/YYYY, DD-MM-YYYY, DD/MM/YY, DD MMM YYYY, DD-MMM-YY and YYYY-MM-DD. Day-first by default; resolve ambiguity from the statement period and monotonic ordering. When rows omit the year, infer it from the period (handle the Dec → Jan rollover). Repair OCR confusions inside date tokens (O→0, l→1). Output ISO-8601; keep value_date separately.
• Amounts. Indian (1,23,456.78) and international (123,456.78) grouping; currency tokens (₹, Rs., INR); parentheses or leading/trailing minus; Dr/Cr suffixes; placeholders (-, --, NIL, blank) become null; quantize to 2 decimals with Decimal. Blank means null, never 0.
• Direction with a single Amount column. Explicit Dr/Cr or Type column → sign → balance delta (authoritative whenever balances exist).
• Balances. Support Cr/Dr suffixes and negative (overdraft) values. Detect opening-balance, closing-balance, brought-forward, carried-forward and total rows and treat them as statement metadata, not transactions.
• Narration. Keep description_raw verbatim (whitespace-normalized, Unicode NFKC); produce description_clean; extract ref_no (cheque/UTR/RRN), channel (UPI, NEFT, RTGS, IMPS, ATM, POS, ECOM, NACH/ECS, CHEQUE, INTEREST, CHARGES, OTHER) and counterparty (see 4.11).
• Ordering. Detect ascending or descending order from dates and the balance chain; keep seq (original order) and ordinal (chronological).
4.9 Account-holder and statement metadata
Extract the D7 fields, each with value, confidence and source page/box. Method: label–value extraction using a synonym dictionary (Account Name / Customer Name / A/c Holder; Account No / A/c No; IFS Code / IFSC; MICR; Branch; CIF / Customer ID; Account Type; Statement Period / From–To; Address; Email; Mobile), searching right of the label and then below it, followed by validation (IFSC ^[A-Z]{4}0[A-Z0-9]{6}$, 9-digit MICR, email format, account numbers of 9–18 digits, masked forms such as XXXXXX1234). Bank detection order: IFSC prefix (SBIN, HDFC, ICIC, UTIB, KKBK, PUNB, BARB, CNRB, YESB, IDFB, …) → header keywords or logo text → layout fingerprint → unknown. Strip honorifics from names; keep multi-line addresses. If several accounts appear in one PDF, split per account or flag MULTIPLE_ACCOUNTS. Every field is user-editable; edits are stored and flagged.
4.10 Validation, reconciliation and auto-repair
For consecutive rows, expected_balance = previous_balance − debit + credit; a row passes when the absolute difference from the printed balance is ≤ 0.01 (the first row uses the opening balance when known). Repair order — stop at the first success, always keep the raw_* values, record repair metadata and set a flag:
1. derive direction from the balance delta;
2. swap debit and credit;
3. bounded OCR-confusion substitutions (O↔0, I/l↔1, S↔5, B↔8, Z↔2, G↔6, comma↔dot, lost decimal point; at most 2 edits), accepted only if the equation then holds;
4. infer a missing or illegible amount from the balance delta (INFERRED_AMOUNT);
5. infer a missing balance from the trusted previous balance (INFERRED_BALANCE).
Rows that still fail get BALANCE_MISMATCH (expected vs actual vs delta); if the delta looks like a skipped row, add POSSIBLE_MISSING_ROW.
Statement-level checks: opening + Σcredits − Σdebits = closing; compare with printed summary totals and counts when present; dates within the statement period and monotonic; duplicate rows created by overlapping pages. Compute a row confidence (OCR confidence of date/amount/balance tokens, balance-check result, column-fill completeness, date certainty) and a 0–100 statement quality score with a plain-language explanation.
Flag vocabulary: BALANCE_MISMATCH, INFERRED_AMOUNT, INFERRED_BALANCE, POSSIBLE_MISSING_ROW, LOW_OCR_CONFIDENCE, REPAIRED_OCR, DATE_OUT_OF_PERIOD, DATE_NON_MONOTONIC, POSSIBLE_DUPLICATE, LOW_CONFIDENCE, CLASSIFIER_DISAGREEMENT, MULTIPLE_ACCOUNTS.


=== SECTION ===
4.11 Classification engine (non-LLM)
Taxonomy (editable taxonomy.yaml; category → optional subcategory; each category has direction: credit | debit | both).
• Income: Salary & Wages · Business/Freelance Income · Interest Earned · Dividends · Rental Income · Refunds & Cashbacks · Investment Redemptions · Transfers In (P2P/Self) · Other Income.
• Expenses: Food & Dining · Groceries · Shopping & E-commerce · Transport & Fuel · Travel & Lodging · Utilities & Bills · Rent & Housing · Healthcare & Pharmacy · Education · Entertainment & Subscriptions · Insurance · Loan EMI & Repayments · Credit Card Payments · Investments & Savings · Taxes · Bank Charges & Fees · Cash Withdrawal · Cash Deposit · Transfers Out (P2P/Self) · Donations & Gifts · Personal Care & Fitness · Government & Fees · Other / Uncategorized.
Layer 0 — normalization (normalize.py): uppercase; strip URLs, long digit runs (6 or more), masked card numbers, IFSCs and timestamps; split channel prefixes (UPI, NEFT, IMPS, RTGS, ATM, POS, ECOM, NACH, ECS, CHQ, INT); keep the VPA handle as a feature (swiggy@icici → SWIGGY); collapse separators (/ - _ . *); apply a merchant alias map (AMZN and AMAZON PAY → AMAZON); fuzzy-match tokens against the merchant dictionary (RapidFuzz ≥ 90, guarded against false positives). Extract counterparty with per-channel patterns (UPI: first alphabetic segment after the 12-digit RRN; NEFT/IMPS: beneficiary name). A person-like counterparty (2–3 alphabetic tokens, no merchant keyword, phone-number or generic-bank VPA) is treated as P2P.
Layer 1 — heuristic rule engine (rules/*.yaml, hot-reloadable): each rule has id, category, subcategory, direction, priority, match (any, all, none, regex), optional amount_range and channel, confidence and note. Use an inverted keyword index for speed; score = priority + specificity (matched length and token count); ties go to the longer match, then the lower rule id. Return the winning rule, the top 3 candidates and the matched tokens — explainability is mandatory. Ship at least 300 keywords/merchants covering common Indian merchants and narration patterns (for example Swiggy/Zomato, Amazon/Flipkart/Myntra, Uber/Ola/IRCTC/FASTag, Jio/Airtel/Vi, state electricity boards, LIC, Zerodha/Groww, Netflix/Hotstar/Spotify, DMart/BigBasket/Blinkit/Zepto, ATM WDL, SMS/AMC/MIN BAL charges, GST/IGST/CGST/SGST on fees, SALARY/SAL, INT.PD, EMI/NACH loan debits, SIP/MF).
Layer 2 — traditional ML (classification/ml): scikit-learn pipeline: TF-IDF word 1–2-grams plus char_wb 3–5-grams on the cleaned text, plus direction, channel and log-amount-bucket features → LinearSVC with probability calibration (or class-balanced Logistic Regression; pick by cross-validation). Training data: (a) a synthetic seed set of at least 2,000 labelled narrations generated from realistic templates with spelling noise, truncation and channel prefixes; (b) high-confidence rule labels (weak supervision); (c) user corrections. Evaluate on a hand-written held-out set of at least 300 realistic rows that is never used for training or rule tuning; save per-class precision/recall, macro-F1 and a confusion matrix to docs/CLASSIFICATION.md. Persist with joblib plus a metadata JSON (version, date, labels, metrics, data hash); fix random seeds so training is deterministic. State plainly in the README that this benchmark is synthetic.
Layer 3 — contextual heuristics (context.py): recurring-payment detection (same normalized counterparty, at least 3 occurrences, 7/14/28–32-day cadence, amount variance ≤ 10 %) that boosts Rent, EMI, Subscriptions and Salary; self-transfer matching across a workspace’s statements (equal amounts, ±1 day, opposite directions), excluded from income and expense totals; refund/reversal pairing (a REV/REFUND/RETURN credit matching an earlier debit within 45 days → reversal_of); fee + GST pairing on the same date.
Hybrid decision: (1) rule match with confidence ≥ 0.80 → source RULE; (2) otherwise ML probability ≥ 0.60 → ML (an agreeing lower-confidence rule boosts confidence); (3) rule and ML disagree with both ≥ 0.80 → keep the rule and flag CLASSIFIER_DISAGREEMENT; (4) otherwise Other / Uncategorized with LOW_CONFIDENCE — never force a guess; (5) MANUAL corrections always win and are never overwritten by reclassification. Store category, subcategory, source, confidence, rule id, ML top 3, explanation tokens and the model/rule-set version.
Learning loop: after a correction, offer Apply to N similar (same counterparty or description similarity ≥ 0.9) and Create rule from this (pre-filled). Corrections are stored per workspace, applied immediately as exact-match overrides, and used as extra training data on POST /classifier/retrain.
4.12 Data model and persistence
Tables (UUID primary keys, workspace_id on every row, timestamps): workspaces, statements, statement_pages, transactions, categories, rules, corrections, classifier_models, jobs. Amounts are BIGINT minor units (paise), nullable where unknown. Indexes: (statement_id, seq), (workspace_id, txn_date), (workspace_id, category), unique (workspace_id, sha256). Alembic migrations; no SQLite-only features; a repository layer so DATABASE_URL can point at Postgres unchanged.
• statements: filename, sha256, bank code/name, pdf_type, page_count, status, stage, quality_score, the D7 fields, period_start/period_end, opening/closing balance, currency, warnings (JSON), strategy_used, parser_version, created_at, expires_at.
• statement_pages: page_no, page_type, rotation, ocr_quality, width, height, image cache path.

4.15 Edge-case catalog (mandatory)
Implement every item below or mark it explicitly “partial” or “unsupported” with the reason in docs/EDGE_CASES.md; each item needs at least one test.
File level
• Password-protected, corrupted/truncated, zero-byte, non-PDF renamed to .pdf, oversized or too many pages, duplicate upload.
• Mixed text and scanned pages; rotated, landscape or upside-down pages; skewed, low-DPI (< 150), faint, noisy or shadowed scans; phone-photo scans (best effort plus a warning).
• Invisible or low-quality OCR text layer; fonts without Unicode mapping ((cid:N)).
• Several accounts or statements in one PDF; very large statements (10,000+ rows); non-statement PDFs (invoice, letter) and credit-card statements → clear error or warning, never garbage output; a valid statement with zero transactions → valid empty result.
Layout level
• Separate Debit/Credit columns vs one Amount column with Dr/Cr, sign or a Type column; borderless vs ruled tables; zebra shading; merged cells; two-line headers; headers not repeated on continuation pages; running headers, footers and watermarks; multi-line narrations; narrations containing amount-like or date-like numbers; separate transaction and value dates; cheque/reference columns; newest-first vs oldest-first; opening, closing, brought-forward, carried-forward and total rows; summary tables after the transactions.
Parsing level
• Two-digit years, month names, missing year, Dec → Jan rollover, ambiguous DD/MM vs MM/DD.
• Indian vs international digit grouping, currency symbols, parentheses or trailing minus, Dr/Cr suffix on amounts and balances, overdraft balances, -/NIL placeholders, zero amounts.
• OCR confusions (O/0, l/1/I, S/5, B/8, comma/dot, lost decimal point); NBSP and zero-width characters; Devanagari digits (best effort).
Integrity level
• Balance mismatch, missing rows, totals mismatch against the printed summary, out-of-period or non-monotonic dates; identical same-day transactions that are legitimate vs duplicates created by overlapping pages or statements (decide by the balance chain; never drop silently).
• Merging several statements of the same account: sort chronologically, de-duplicate overlaps, flag period gaps (balance-chain break).
Classification level
• Unknown merchants → Other / Uncategorized plus the review queue; the same narration in opposite directions; P2P vs merchant UPI; self-transfers; wallet top-ups; refunds and reversals; fee + GST pairs; cash deposits and withdrawals; cheque numbers only; truncated or noisy narrations; transliterated or abbreviated merchant names; rule conflicts surfaced to the user; rule-set and model version stored, with “Reclassify all” that never touches manual edits.
Export level
• Formula injection; leading zeros in account and reference numbers preserved as text; Excel row, length and sheet-name limits; UTF-8 BOM; locale separators; filename sanitization; empty selection disables export with an explanation; edited categories and filtered views exported faithfully.
UX level
• Network drop and retry with resumable status; refresh during processing; cancel; concurrent uploads; undo; large-table performance; keyboard-only operation; 360 px layout.

6. STEP-BY-STEP IMPLEMENTATION PLAN
6.1 Build Protocol (applies to every reply)
1. Build incrementally — one step per reply, then stop. Never emit the whole system at once.
2. Reply 1 is Step 0 and contains no code: (a) a restatement of the goal in at most 10 lines; (b) the confirmed defaults D1–D10 and at most 3 truly blocking questions (otherwise state your assumptions and proceed); (c) the final repository tree; (d) the dependency list, with versions you are certain exist; (e) top risks and mitigations. Then wait for “continue”.
3. Every later reply: header STEP n — title; list of files created or changed; the complete contents of every file in fenced blocks, each preceded by a path comment; no placeholders, ellipses or “rest unchanged”; at most ~300 lines per file (split modules instead); when editing, re-emit the full file or an exact unified diff.
4. End each step with: How to run and test (exact commands) · Acceptance checklist (each criterion ticked or explained) · Known limitations · then the line Reply “continue” for STEP n+1 and stop.
5. Ship tests with the code they cover. Never claim a test passed unless you ran it; if you cannot execute code, say so and give the expected output.
6. If you are near the output limit, stop at a file boundary, list the remaining files and wait.
7. Prefer mainstream, permissively licensed libraries. Do not guess APIs — wrap uncertain calls in a small adapter with a test. Maintain docs/DECISIONS.md (one-line ADRs) and docs/EDGE_CASES.md (scenario → behaviour → test name) as you go.

7. COMPLIANCE & PERFORMANCE STANDARDS
7.1 Security (OWASP Top 10 / ASVS Level 1 mindset)
• Treat every PDF as hostile: validate magic bytes; never execute embedded actions or JavaScript; run parsing and OCR in worker processes with timeouts and memory/pixel caps (decompression-bomb defence); reject or flag suspicious structures.
• Validate all input with Pydantic; use parameterized queries through the ORM; rely on React’s output escaping and never use dangerouslySetInnerHTML for narrations; strict CSP, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, frame-ancestors 'none', HSTS in production; CORS allow-list; rate limiting (slowapi); sanitized Content-Disposition filenames.
• Secrets only from the environment; .env git-ignored; pinned dependencies; pip-audit and npm audit in CI.
• Signed HttpOnly SameSite cookies; workspace scoping on every query (tested); CSV/Excel formula-injection defence (4.13).
7.2 Privacy and data protection
Design principles aligned with India’s DPDP Act 2023 and GDPR (not legal advice): data minimization; purpose limitation (statement data is used only to produce the user’s outputs); notice on the upload screen and on /privacy; a retention limit with auto-purge and hard delete (files, page images, DB rows, caches); optional encryption at rest; no analytics or third-party trackers; account numbers masked in the UI and logs by default; PDF passwords never stored; redacted debug bundles only.

7.5 Performance budgets
Measure on a 4-vCPU / 8 GB reference machine and record the results in the README.
• Text PDF, 10 pages: 5 s or less end to end (p95). Scanned PDF at 300 DPI: 3 s or less per page amortized with page parallelism (a 20-page scan in 60 s or less).
• Classification: at least 2,000 transactions per second (rules + ML batch inference). Export of 10,000 rows: 5 s or less (xlsx), 2 s or less (csv).
• API: p95 of 300 ms or less for list and filter endpoints at 10,000 rows (indexed, paginated, server-side).
• Frontend: initial JS of 200 KB gzip or less for the shell (route- and chart-level code splitting); LCP ≤ 2.5 s, CLS ≤ 0.1, INP ≤ 200 ms; Lighthouse performance of at least 90 and accessibility of at least 95 on the shell; the grid stays smooth with 10,000 rows (virtualization).
• Resource safety: bounded queue, backpressure, per-job timeouts and memory caps; never keep unbounded page images in memory.
